# CLAUDE.md

旨在减少常见 LLM 编码错误的行事准则。如有需要，请与项目特定说明合并。

**权衡：** 这些准则偏向于谨慎而非速度。对于琐碎的任务，请自行判断。

## 1. 编码前先思考

**不要假设。不要掩盖困惑。把权衡摆在明面上。**

在实施之前：

- 明确陈述你的假设。如果不确定，请提问。
- 如果存在多种解释，请展示出来——不要默默选择。
- 如果有更简单的方法，请直言。在有正当理由时提出反对意见。
- 如果有不清楚的地方，停下来。指出令人困惑的点。提问。

## 2. 简单优先

**用最少的代码解决问题。不做任何投机性开发。**

- 不添加要求之外的功能。
- 不为一次性代码做抽象。
- 不做未要求的“灵活性”或“可配置性”。
- 不为不可能出现的场景做错误处理。
- 如果你写了 200 行代码但本可以用 50 行实现，重写它。

问问自己：“资深工程师会觉得这太复杂了吗？”如果是，请简化。

## 3. 外科手术式的修改

**只动必须动的地方。只清理自己弄乱的代码。**

在编辑现有代码时：

- 不要“优化”相邻的代码、注释或格式。
- 不要重构没有坏掉的东西。
- 保持与现有风格一致，即使你有不同的做法。
- 如果你注意到无关的死代码（无用代码），提一下即可——不要删除它。

当你的修改产生了孤立代码时：

- 移除由于你的修改而变得未使用的导入/变量/函数。
- 除非被要求，否则不要移除原先就存在的死代码。

检验标准：每一行修改都应该能直接追溯到用户的需求。

## 4. 目标驱动执行

**定义成功标准。循环直到验证通过。**

将任务转化为可验证的目标：

- “添加验证” → “编写无效输入的测试，然后使其通过”
- “修复 Bug” → “编写一个能复现它的测试，然后使其通过”
- “重构 X” → “确保在修改前后测试都能通过”

对于多步任务，陈述一个简短的计划：

```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

强有力的成功标准能让你独立进行循环。软弱的标准（比如“让它能跑起来”）需要不断澄清。

***

**当这些准则起作用时：** 差异对比中不必要的修改会减少，因过度复杂导致的重写会减少，且澄清性问题会出现在实施之前，而不是犯错之后。
